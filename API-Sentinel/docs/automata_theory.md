# Formal Language & Automata Theory in API Sentinel

## 1. Introduction & Theoretical Foundations
Compilers, domain-specific languages (DSLs), and deterministic state machines are rooted in **Chomsky's Hierarchy of Formal Languages**:
1. **Type 3 (Regular Languages)**: Recognized by Finite State Automata (DFA/NFA). Used in the **Tokenizer** for lexical token extraction.
2. **Type 2 (Context-Free Languages)**: Generated by Context-Free Grammars (CFG) and recognized by Pushdown Automata. Used in the **ASL Parser** for hierarchical syntax structures.
3. **Type 1 (Context-Sensitive Languages)**: Semantic checks, symbol resolution, and DAG cycle detection.
4. **Type 0 (Unrestricted / Turing Complete)**: General computation.

---

## 2. Lexical Analysis (Scanner / Tokenizer)
The Lexer processes a raw character stream $C = c_1, c_2, \dots, c_n$ and transforms it into a discrete sequence of typed token tuples:

$$\tau = \langle \text{TokenType}, \; \text{Lexeme}, \; \text{Line}, \; \text{Column} \rangle$$

### Deterministic Lexing Strategy:
- **Whitespace & Comments**: Skips single-line `// ...` and multi-line `/* ... */` using bounded lookahead.
- **Line & Column Tracking**: Tracks line counter increments upon encountering `\n`, resetting column counter to 1, providing exact compiler diagnostic coordinates.
- **Escape Processing**: Decodes character escapes (`\n`, `\t`, `\"`, `\\`) within string literals.

---

## 3. Context-Free Grammars & Recursive-Descent Parsing
The ASL syntax is defined as a Context-Free Grammar $G = (V, \Sigma, R, S)$:
- **$V$**: Non-terminal variables ($\text{Workflow}$, $\text{StepList}$, $\text{Step}$, $\text{StatementList}$, $\text{Statement}$).
- **$\Sigma$**: Terminal alphabet of tokens.
- **$R$**: Production rules.
- **$S$**: Start symbol ($\text{Workflow}$).

### LL(1) Recursive-Descent Implementation
The parser is implemented without external parser generators (e.g. Yacc, Bison, ANTLR). It employs an **LL(1) Top-Down Recursive-Descent Parser** with single-token lookahead ($\text{peek}(0)$):

```
parseWorkflow()
  ├── consume(KEYWORD_WORKFLOW)
  ├── consume(IDENTIFIER)
  ├── consume(LBRACE)
  ├── parseStepList()
  │     ├── parseStep()
  │     │     ├── consume(KEYWORD_STEP)
  │     │     ├── consume(IDENTIFIER)
  │     │     ├── consume(LBRACE)
  │     │     ├── parseStatementList()
  │     │     └── consume(RBRACE)
  │     └── [recurse or terminate upon RBRACE]
  └── consume(RBRACE)
```

## 4. Abstract Syntax Tree (AST) Construction
Unlike parse trees (which represent concrete grammar derivations), the AST strips syntactic punctuation (braces, semicolons, whitespace) and captures the structural semantics of the workflow:

```
WorkflowNode: {
  type: "Workflow",
  name: "ECommerceOrderPipeline",
  steps: [
    StepNode: {
      type: "Step",
      name: "UserAuthentication",
      config: {
        method: "POST",
        url: "/api/demo/login",
        expectedStatus: 200,
        retries: 2,
        timeoutMs: 5000,
        extract: { authToken: "body.token" }
      }
    },
    ...
  ]
}
```

## 5. Semantic Analysis & DAG Cycle Detection
Syntactic correctness does not guarantee semantic validity. The semantic validator enforces:
1. **Symbol Table Check**: Verifies that every step identifier is globally unique within the workflow.
2. **Referential Integrity**: Verifies that any step referenced in `DEPENDS` exists.
3. **Directed Acyclic Graph (DAG) Verification**:
   Workflow step execution dependencies form a directed graph $G = (V, E)$. To ensure execution cannot stall in an infinite deadlock:
   - A Depth-First Search (DFS) graph coloring algorithm is executed:
     - White ($0$): Unvisited node.
     - Gray ($1$): Currently on recursive exploration stack (visiting).
     - Black ($2$): Completely explored (visited).
   - If a directed edge $u \to v$ leads to a node currently marked Gray ($1$), a back-edge exists, proving a cycle. The validator immediately rejects the AST with a comprehensive path trace:
     `"Cyclic dependency detected: StepA -> StepB -> StepA"`.
